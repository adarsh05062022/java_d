The Six-Column Test

Task 5 showed GRDM destroys exactly one kind of information: statistics summarising a child table. So we gave it those statistics directly — six columns, nothing else changed — and retrained. This is what we did, why we did it that way, and what came back.

Dataset  berka_split_agg Baseline  berka_split Seeds done  2 of 3 Metric  synthetic→real AUROC

The 30-second version

Card ownership: synthetic→real AUROC went 0.607 → 0.665. Loan default: 0.543 → 0.593. Measured as how much of the real model's skill survives into synthetic data, that is 29% → 45% on card and 12% → 26% on loan.

The hypothesis was right in direction: the missing signal really is child-aggregate information, and exposing it helps. But more than half the gap remains — denormalising the statistics is a partial fix, not a solution.

1

The diagnosis we were acting on

Task 5 measured, for each feature, how strongly it predicts the label inside the real database and inside the synthetic one — a univariate AUROC, no model involved. Sorting those features by where they come from in the schema produced a clean split:

Task 5 — fraction of real feature→label signal surviving generation
Feature familyWhat it isCardLoan
Own row / 1-hop parenta field of the labelled row, or of a table it points straight at41%99%
Child aggregatea statistic rolled up over a child table (trans, order)11%13%

The sharpest single case: trans_balance_mean is worth 0.838 univariate AUROC in real data and 0.511 in synthetic — 3% retained, with the synthetic confidence interval covering 0.5 in all three seeds. The relationship isn't weakened; it is absent. And trans_balance_last shows it isn't a broken column: its marginal distribution still matches the real one almost exactly (KS 0.045), while its connection to the label is gone.

Why this points at aggregation

GRDM runs with n_hops=1, num_neighbors=[-1], gnn_aggr=sum. It sees all of an account's ~235 transactions — but collapses them into a single summed vector. One statistic per neighbourhood. A model that only ever receives the sum cannot condition a row on the mean, the last value, the spread, or the count — which is precisely the list of features that died.

2

The hypothesis, stated so it can fail

If the missing downstream signal is caused by child-aggregate statistics never reaching the denoiser, then handing those statistics to the model as ordinary columns should raise synthetic→real AUROC.

That is falsifiable in a useful way. If the number doesn't move, the aggregation bottleneck is not the mechanism and Task 5's story — however tidy — is wrong about causation. The baselines to beat were fixed in advance by the Task 2/3 cross-domain run: 0.607 on card, 0.543 on loan (seeds 1–2, the like-for-like subset).

3

Designing the intervention

Six account-level rollups were chosen — the ones Task 5 actually measured, so the test lines up with the diagnosis:

agg_trans_n              # fan-out: how many transactions this account has
agg_trans_balance_mean   # worth 0.838 univariate AUROC in real data
agg_trans_balance_last   # keeps its marginal (KS 0.045), loses its meaning
agg_trans_amount_mean
agg_order_n              # fan-out of the second child table
agg_order_amount_sum

The decision the experiment actually turns on

Writing them onto account is the obvious move — and on its own it would not have worked for the card task. The card label lives on the card table, whose only parent is disp. With n_hops=1, generating a card row conditions on disp and nothing further. account is two hops away: still outside the window.

So the same six columns were denormalised onto both account and disp.

One thing deliberately excluded

No transaction operation-code shares were added. VYBER KARTOU ("card withdrawal") is a deterministic consequence of holding a card — the downstream task drops it for exactly that reason. Exposing it here would have handed the generator the label and produced a meaningless win.

4

Building the dataset

downstream/build_agg_dataset.py copies data/berka/split_train and rewrites two tables. The aggregates are computed from the real training split only — 792,600 transaction rows and 4,874 order rows, grouped to 3,375 accounts — so no test information enters anywhere.

ordered = trans.sort_values(["account_id", "trans_date"])
g = ordered.groupby("account_id")
agg = pd.DataFrame({
    "agg_trans_n":            g.size(),
    "agg_trans_balance_mean": g["balance"].mean(),
    "agg_trans_balance_last": g["balance"].last(),   # needs the sort above
    "agg_trans_amount_mean":  g["amount"].mean(),
})
go = order.groupby("account_id")
agg_o = pd.DataFrame({"agg_order_n": go.size(),
                      "agg_order_amount_sum": go["amount"].sum()})

# An account with no standing orders genuinely has zero, not a gap.
out[["agg_order_n", "agg_order_amount_sum"]] = out[[...]].fillna(0.0)

Then the columns are joined on and the schema grows:

# account.csv
  before: account_id, district_id, frequency, account_date
  after:  account_id, district_id, frequency, account_date, agg_trans_n, agg_trans_balance_mean,
          agg_trans_balance_last, agg_trans_amount_mean, agg_order_n, agg_order_amount_sum

# disp.csv
  before: disp_id, client_id, account_id, disp_type
  after:  disp_id, client_id, account_id, disp_type, agg_trans_n, ... agg_order_amount_sum
The easy-to-miss step

Each new column must be registered in {table}_domain.json as {"size": 0, "type": "continuous"}. GRDM's utils.sort_columns treats any column absent from the domain file as an ID column — so without this the six columns would have been silently carried along as keys and never diffused at all. The experiment would have run to completion and reported a null result for the wrong reason.

5

What deliberately did not change

For the result to be attributable to the aggregates, everything else had to be held fixed. The entire config difference is two lines — which directory to read:

< "dataset_name": "berka_split",       > "dataset_name": "berka_split_agg",
< "data_path": "data/berka/split_train" > "data_path": "data/berka/split_train_agg"

Unchanged: n_hops=1, num_neighbors=[-1], gnn_aggr=sum, d_layers, num_timesteps=2000, learning rate, 200,000 training steps, the train/test cut, 3 GRDM × 5 XGBoost seeds, and every downstream feature builder and metric.

The clearest evidence the control held: real→real AUROC moved by +0.0009 on card and 0.0000 on loan. The real data didn't change, so that cell must not move — and it didn't.

6

Why the evaluation can't cheat

This is the part worth being careful about, because it looks like it should be circular: we injected trans_balance_mean, and we then measure whether trans_balance_mean predicts the label. Doesn't the model just get handed the answer?

No — because the downstream evaluation never reads the injected columns. Its feature builders select account and disp fields by name (account_id, district_id, account_date, frequency) and then recompute every aggregate from the generated child tables. Verified: agg_ appears nowhere in downstream/tasks.py, and the evaluated matrices are still 90 columns (card) and 97 (loan), exactly as in the baseline.

So what does an improvement actually require?

A whole chain has to hold. GRDM must generate a disp.agg_* value; generate a card row whose existence correlates with it; generate trans rows conditioned on account.agg_*; and those generated transactions must then re-aggregate to something close to the value the account declared. Only then does the recomputed trans_balance_mean carry signal about card ownership. Nothing in the loss function enforces that consistency — which is why this is a real test and not a tautology.

7

Running it

Three seeds, 200,000 steps each, launched with a 20-hour per-process wall-clock budget. Worth recording honestly, since it shaped the timeline:

  • All three seeds hit the 20 h budget before finishing (at 85% / 95% / 88%) and exited through their designed checkpoint-and-relaunch path. No progress lost, but a resume was needed — the node was 5–7× slower than the original baseline run because all 8 GPUs were at 70–100% utilisation from other jobs.
  • On resume, seeds 1 and 2 finished training and sampling, then crashed in a cosmetic post-hoc fidelity report — sdv metadata doesn't know about the new agg_* columns. The synthetic databases were already written and are fully usable; only the report step failed.
  • Seed 0 hit a genuine CUDA OOM when other jobs claimed 139 GB of its GPU. Resumed from checkpoint on a less contended device; still sampling at the time of writing.

So the numbers below are 2 of 3 seeds, and the baseline is restricted to the same two seeds for a like-for-like comparison.

What held

Card improves in both seeds, and synth→synth rose alongside synth→real. That second point matters: it means the synthetic database now genuinely contains more learnable structure, rather than the improvement being a lucky fit to the real test set. Task 5's core finding was that synth→synth sat at chance — it no longer does.

What didn't — and needs saying

Loan is seed-dependent. Seed 2 gains +0.095, seed 1 gains +0.006. Same fragility loan shows everywhere in this study; card is the trustworthy read.

real→synth did not improve — flat on card, and worse on loan (−0.087). A real-trained model still doesn't transfer onto synthetic rows even though a synthetic-trained one now transfers better onto real. That asymmetry says the synthetic data has acquired a relationship that is related to but not identical with the real one.

Most of the gap is still open. 0.665 against a real-data ceiling of 0.870 is a partial recovery. Denormalising aggregates helps; it does not fix relational generation.

9

What this changes, and what to check next

  • The causal claim now has support. Task 5 established a correlation between schema distance and signal loss; Task 6 intervened on exactly that variable and moved the outcome, in the predicted direction, on the task with reliable statistics.
  • The bottleneck is architectural, not incidental. A fix delivered entirely through the input representation — without touching n_hops, the pooling operator, or the loss — recovered a third of the missing card signal. That points at gnn_aggr=sum and one-hop conditioning as the thing to change next, rather than at training length or capacity.
  • The unmeasured link in the chain. We have not yet checked whether generated trans rows actually re-aggregate to the agg_* value their parent account declares. Nothing in the loss enforces it. Measuring that consistency would say how much of the remaining 55% is lost at that specific joint — and it is cheap to compute from data already on disk.
  • Finish the third seed. Seed 0 is still sampling. Card's effect is consistent across two seeds, but the loan arm needs the third before any claim about it is worth making.
