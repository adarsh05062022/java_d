Summary

This study asked whether synthetic relational databases generated by GRDM are useful for training predictive models, in addition to whether they look statistically like the real database. We reproduced the paper's fidelity results, measured downstream utility on two databases, located the cause of the failure on the deeper one (Berka), and tested fixes. Acronyms and experiment codes are defined in the glossary (§14); dotted terms show their expansion on hover.

  1. The paper's fidelity numbers reproduce. Berka lands within 0.37 points of the paper on every metric and California within 0.32. CCS matches within 0.1 except 1-HOP, which is 2.77 points low, still inside one paper standard deviation. §4
  2. Fidelity does not predict utility. Models trained only on synthetic California data keep 95–99% of the real-data signal. On Berka they keep 3% (loan default) and 27% (card ownership), although Berka's fidelity scores are only a few points lower (Column Shapes 96.8 against 98.6). The ranking also inverts across models: ClavaDDPM, which trails GRDM on every Berka metric in the paper's Table 1 (3-HOP 80.98 against 92.43), keeps 60% of the card signal and 43% of the loan signal where GRDM keeps 29% and 7% under the same protocol. §5, §5.5
  3. On both Berka tasks, what is missing is the dependency between tables. Card ownership keeps its rate (16.8% real, 16.0–16.7% synthetic) and still loses most of its signal. Loan default also loses its rare outcome: unpaid finished loans (class B) drop from 24 real rows to 1–10 synthetic ones. That collapse is not the main cause of the loan failure: restoring class B exactly (S1) lifts loan only from 3% to 14%, with one of three seeds falling, while ClavaDDPM, which keeps the marginals and more of the dependency, retains 43%. §5, §7.1
  4. The missing signal sits in child-table aggregates. Per-account transaction counts, balances and amounts carry most of the predictive power, and they are two or three foreign-key hops from the labelled row. GRDM conditions each row on its direct neighbours only, pooled by a single sum. After generation, aggregate features keep at most 11% of their link to the label, and about zero among the features with a confirmed real signal; features of the row itself and its direct parent keep 41–99%. §6, §9
  5. The synthetic data is empty rather than wrong. A model trained and tested inside synthetic Berka scores 0.594 AUROC on card ownership, close to chance. There is no alternative relationship to correct for, so re-weighting or domain adaptation would not help. §9
  6. Fourteen fix variants were scored; none reaches 50% on both tasks. Best three-seed results: reparam + S10 (date reparameterisation, two hops, balanced seeds and exact child counts) for loan at 43.6%, with card at 34.5%; S5 (two hops plus balancing) for card at 50.4%, with loan at 24.9%. agg, which copies six child aggregates onto the parent tables without changing the model, is the best combined result at 35.8% loan and 48.7% card, and every agg seed beats every baseline seed on both tasks. §7, §10
  7. Repairing visible symptoms does not restore utility. Fixing the categorical marginals (S1, S4, discrete) or repairing every temporal, ledger and logical constraint after sampling (repair) leaves card utility at baseline and adds at most 13 points on loan, with one seed in three below the baseline, against 33–40 points for the fixes that add cross-table information (agg, reparam + S10). §7, §8
  8. Loan-default results need three seeds. The loan test set has 19 positive cases. Single generator seeds differ by up to 0.24 AUROC, and seed 0 alone overstated S3 (53% against 32% at three seeds), S5 (37% against 25%) and reparam (17% against −3%). Card ownership varies much less. §7.3
  9. Position. As published, GRDM is not reliable for multi-hop predictive tasks on deep schemas such as Berka or the planned AmEx dispute schema. Any evaluation of it needs a downstream-utility gate and a dependency gate alongside fidelity. The most promising direction is to put cross-table aggregates into the generator's input (agg), turned into a schema-wide rule and combined with S3 or with exact child counts (S10). §11, §13

Background and scope

2.1What GRDM does

GRDM (Ketata et al., NeurIPS 2025) treats a relational database as one graph: every row is a node and every foreign-key link is an edge. It generates a synthetic database in two stages.

  • Structure first. A random graph sampler draws how many child rows each parent gets from the real degree distribution of that relationship, and matches rows of multi-parent tables. No attribute values exist at this point.
  • Attributes second. All rows are denoised together by a Gaussian DDPM with T = 2,000 steps. The denoiser is a heterogeneous GraphSAGE network with sum aggregation that reads each row's K-hop neighbourhood, followed by a per-table MLP head. The published configuration uses K = n_hops = 1.
  • Categoricals as numbers. Categorical columns are label-encoded as integers, quantile-transformed together with numeric columns, diffused as continuous values and rounded back.
  • Dimension tables. Lookup tables such as Berka's district are held fixed and only conditioned on.
  • Training. Each step draws a seed row uniformly at random, noises it together with its neighbourhood and computes the loss on the seed row only.

The paper reports state-of-the-art fidelity, with its largest margins on multi-hop correlations: on Berka, 3-HOP trends of 92.43 against 80.98 for ClavaDDPM, the strongest earlier method.

Methodology

The study used four kinds of measurement: the paper's own fidelity metrics, downstream models trained on synthetic data, closed-form dependency checks with no model involved, and targeted diagnostics. Every intervention was isolated so that a change in the numbers can be attributed to it.

3.1Fidelity reproduction

  • Code and configuration. Official repository at commit bc0fb67 with the paper's hyperparameters (Appendix D.2.1): K = 1, T = 2,000, learning rate 6e-4, weight decay 1e-5, batch 4,096, cosine schedule, 200,000 training steps (100,000 for California). The only configuration change is the sampling batch size, 20,000 → 100,000. Sampling uses full neighbourhoods, so batch grouping is scheduling only and cannot change results.
  • Seeds. Three seeds per database. In this code base a seed retrains the model from scratch, so three seeds are three full trainings.
  • Metrics (SDMetrics, as in the ClavaDDPM and GRDM papers; 0 = worst, 100 = best). Cardinality compares the number of child rows per parent. Column Shapes compares each column's marginal distribution (KS for numeric, TV for categorical). Intra-Table Trends compares the correlation of every column pair inside a table (Pearson for numeric, contingency tables for categorical). k-HOP (inter-table trends) does the same for column pairs from tables k foreign-key links apart. AVG 2-WAY averages all pair scores.
  • Required local fixes, none of which changes the method: np.concat → np.concatenate for NumPy 1.26; checkpoint and resume, because the cluster kills processes after about 24 hours; a relaxed label-encoding assertion that crashed on the train split (a client birth year that only occurs in test rows); deterministic column order in output files.
  • Judging the match. By absolute deviation, not by standard deviations. The paper's reported spreads are very tight (some ±0.03), so a 0.1-point gap can look like three sigma while meaning nothing.

  • Training regimes. Real only. Synthetic only, subsampled to the real training row count so that the comparison is about quality rather than quantity. Augmentation: the full real set plus 25%, 50% or 100% extra synthetic rows. Substitution: total rows fixed, with 75/25, 50/50 and 25/75 real-to-synthetic mixes, each compared with a control that keeps the same real rows and simply drops the rest.
  • Model. XGBoost with fixed, untuned hyperparameters, identical in every regime. No early stopping, because an early-stopping set would have to be real data and would leak real rows into the synthetic-only regime.
  • Repeats. 3 GRDM seeds × 5 XGBoost seeds on Berka (15 fits per cell), × 3 on California. Re-running the harness gives byte-identical numbers.
  • Metrics. The primary metric per task, plus average precision, macro-F1, balanced accuracy and accuracy. A 95% bootstrap CI over test rows is reported for the real baseline.
Headline measure: signal retained

retained = (synthetic − floor) / (real − floor), where the floor is 0.5 for AUROC (chance) and 0 for R² and macro-F1. 100% means the synthetic-only model is as good as the real-only one; 0% means it has learned nothing usable; negative means worse than chance. Example: card ownership, real 0.8739 and synthetic 0.6021, gives (0.6021 − 0.5) / (0.8739 − 0.5) = 27.3%.

3.3Leakage control

The first feature sets gave real-data AUROC of 1.0000 on loan default and 0.9805 on card ownership. A near-perfect real baseline on a task like this means a leak, and decoding the label encoders found two:

  • SANKC. UROK (trans.k_symbol = 4) is sanction interest, charged only once an account is already in debt. Fixed by keeping only transactions dated before the loan, which turns the task into a prediction at loan origination. Berka stores each date column as days since that table's own earliest date (transactions from 1 January 1993, loans from 5 July 1993), so the two dates are first put on one day count. A median of 77 earlier transactions remains per loan, every loan has some history, and the code remains in 29 of the 80 loan accounts that ever pay it: sanction interest charged before the loan was granted, which a lender would see. No single feature then exceeds about 0.79 test AUROC. Until 5 October the cut compared the raw stored dates and fell 185 days early.
  • VYBER KARTOU (trans.operation = 5) is a card withdrawal, which cannot exist without a card. Cards are issued long after accounts open (median 658.5 days, epoch-corrected), so no time cut separates cause from effect. The code is dropped and the task is reported as a cross-table dependency probe rather than a forecast.

Leakage-free split. Berka ships without a test split. make_berka_split.py holds out 25% of accounts, stratified on loan outcome. The cut is clean because client and disposition are one-to-one, each account has at most one loan and each disposition at most one card; district stays whole on both sides. GRDM was retrained on the training split only (berka_split). The earlier run that had seen the test rows (berka) differs from it by at most 0.017 AUROC, so leakage was not what made Berka look bad. All Berka results below use berka_split unless marked.

Guards in the harness. No aggregate may be computed from the target column; the card table contributes only the label; train and test IDs are asserted disjoint per table; foreign-key integrity is asserted on real and synthetic tables before features are built; a baseline-identical check (redecode.py --verify) proves that the fix machinery leaves the published path unchanged.

3.4Diagnosis

Four candidate causes (H1–H4) were each given a test that could have ruled it out, plus a sixth diagnostic (A6) added later.

testquestionmethod
A1Does rounding Gaussian-diffused category codes erase rare classes? (H2)Per-class synthetic/real share for every categorical column, 3 seeds, stratified by rarity and by whether the code sits at the edge or inside the code range.
A2Is the generator limited by how far it can see? (H1)Train XGBoost on real data restricted to the row's own columns, then plus one-hop parents (GRDM's window), then everything; compare with the synthetic-only score.
A3Do small tables get enough training signal? (H3)Share of seed rows per table in a 4,096-row batch.
A5Is the relationship absent or just different? (H4)Train and test entirely inside each database: real→real against synthetic→synthetic.
A6Which kind of neighbourhood information is missing?Split child-table features into families (counts, means and sums, spread and extremes, code shares). Measure each family's real predictive value, then its survival as |corrsyn| / |corrreal| with the label.

3.5Fix program design

Each fix changes one thing, is behind a flag that is off by default, writes to its own workspace and is scored on the same split and test set as the baseline. Bit-identity of the default path was verified by comparing every parameter tensor and the forward output of the stock and modified networks under one seed. Every fix that could affect California also ran a California guard: a fix that breaks the database that already works is rejected. 3.6Dependency-fidelity suite

Eight closed-form checks computed the same way on real and synthetic tables, with no classifier, so there is no seed noise from model fitting and no conditioning-depth confound. They prototype the AmEx proposal's quality gates for temporal consistency (Gate 3) and financial consistency (Gate 4).

  • Temporal (3). A child event may not precede its parent: loan_date ≥ account_date, card.issued ≥ account_date (through disp), trans_date ≥ account_date. Berka stores each date column as days since its own earliest value, so every date is converted to a calendar day first.
  • Financial (2). The account's final balance equals the sum of its signed transaction amounts (account level), and every balance step equals the transaction amount (row level). The row-level check reaches only 68.7% on real data because same-day transactions cannot be ordered from a day-resolution date.
  • Logical (3). VYBER KARTOU ⇒ the account holds a card; SANKC. UROK ⇒ the account was overdrawn at some point; a standing order for a loan payment (UVER) ⇒ the account has a loan.
  • Repair. Tier 1 edits finished samples onto the constraint-satisfying set, in dependency order (dates, then ledger, then logical rules), aiming at the real rate rather than 100%. Tier 3 changes the data representation so that a date violation cannot be expressed. Every repair operator is first applied to the real database, where it should change nothing; the balance operator moves it slightly, for a reason given in §8.3.

3.7Mechanism study

Five experiments on the leakage-free generator, 3 GRDM × 5 XGBoost seeds, reusing the harness's feature code and hyperparameters unchanged so the numbers compare directly with §5.

  • Task 1, substitution ladder: fixed training size, real share 100/75/50/25/0%, each against a control that drops rows instead of replacing them.
  • Tasks 2–3, cross-domain matrix: the synthetic database is itself split with the same account-level, outcome-stratified call used for the real one, so a synthetic test set is a held-out relational database. All four train/test combinations use matched training sizes.
  • Task 4, feature provenance: the univariate AUROC of every feature against the label, measured inside each database and grouped by schema distance. No model is involved, so this separates "the generator lost the relationship" from "the classifier ignored it".
  • Task 5, feature-level validation: bootstrap CIs (400 resamples, percentile method) on each univariate AUROC, per seed, with a matched control group from the same task. Retention is averaged only over features whose real CI excludes 0.5.

3.8Six-column test

A direct test of the mechanism. Six account-level rollups computed from the real training split only (agg_trans_n, agg_trans_balance_mean, agg_trans_balance_last, agg_trans_amount_mean, agg_order_n, agg_order_amount_sum) are added as ordinary columns to both account and disp, and registered as continuous columns in each table's domain file, without which GRDM would silently treat them as IDs. The config differs from the baseline only in the data directory. The downstream feature builders select parent columns by name and never read agg_*; every evaluated aggregate is recomputed from the generated transactions and orders, so the injected columns cannot leak into the score.

3.9Statistical conventions

  • "Seed" means a GRDM generator seed, which is a full retraining. "±" is the standard deviation over all repeats (generator × XGBoost seeds) unless stated otherwise.
  • Loan default has 19 positive test cases; its real-only bootstrap CI is [0.870, 0.989]. Loan magnitudes are indicative; card ownership, with 220 positives, carries the firm conclusions.
  • Fidelity values in tables are three-seed means from the training logs unless marked.

3.10Compute and infrastructure

All runs used a shared node with 8 NVIDIA H200 GPUs. A GRDM run needs only about 1.3–1.5 GB of GPU memory, so GPUs were chosen by utilisation rather than free memory, and up to three runs shared a GPU. A Berka seed took 13–14 hours of training plus 1–1.5 hours of sampling on a lightly loaded GPU, and 2–7 times longer when the node was busy. Because the cluster ends processes after about 24 hours, the code gained per-epoch checkpoints, a --max_hours budget shared by training and sampling, sampling checkpoints every 25 timesteps, a self-restarting watchdog and an unattended sweep runner (sweep/run_sweep.sh). None of this changes results.

6.3A1 · rounding of category codes

Averaged over every categorical column the effect is negligible: at matched rarity, classes inside the code range lose no more mass than classes at its edge (median retention 1.00× for classes with 0.5–10% share), and the width of a class's band in quantile space is unrelated to its survival (Spearman ρ = −0.03, n = 237). A prediction that failed, and what it taught

Before the retrains finished, the diagnosis predicted that deeper conditioning (S2) would help loan default and could not help card ownership, because card ownership is decided during structure sampling (H4). The card half was wrong: S2 lifted card from 27.3% to 45.1%. It also lifted loan, from 3.3% to 21.2%; under the shortened loan window used until 5 October it had appeared to cut loan to 6.8%. Structure is sampled first, but attributes are then generated conditioned on it, and n_hops sets how far that information travels. At one hop an account cannot see whether its dispositions hold cards (card is two edges away); at two hops it can, so balance patterns start to correlate with card ownership. A structural label is out of reach only when the structure lies outside the window.

Decoding and sampling: S1, S3

S1 restores every categorical marginal exactly (class B back to 24, 24 and 23 rows; default rate 0.110–0.113 against a real 0.112). The most visible symptom in a fidelity table buys a small, seed-dependent part of the loan signal and none of the card signal. S3 weights seed rows by table size−0.5, giving loan 30 times more training signal per batch. It lifts loan to 32.2%, third among the three-seed results, and is the only fix that also improves fidelity (Column Shapes 96.89, 1-HOP 91.85 against 96.81 and 90.33).

Conditioning depth: S2, S5, S6, S7

Two hops help both tasks. S2 takes card to 45.1% and loan to 21.2%, and adding balanced seeds (S5) gives the best three-seed card result (50.4%) with loan at 24.9%. Under the shortened loan window used until 5 October, depth had appeared to hurt loan default, and an untested batch-dilution account was offered for it; with the corrected window there is nothing to explain at two hops.

Denoiser architecture: S4, S8–S13

S4 (one-hot categoricals) damaged both tasks and collapsed California (R² −4.97, worse than predicting the mean), so it was stopped after one seed. S8–S11 change the network itself, each layered on S5: multi-statistic pooling (S8), residual message passing (S9), exact per-relation child counts (S10) and self-conditioning (S11). It has one seed: its other seeds and the single-flag ablations were stopped when the two-hop line was retired.

For date violations, clamping a child date to its parent's has the smaller marginal distance (0.094 against 0.138) but piles repaired rows onto one day (p10 lag 0.9 days against a real 166). Redrawing the lag from the real lag distribution restores the tail (145.8 days) and is the default.
  • Repair to the real rate, not to 100%. Two logical rules hold for about 94% of real accounts. A database repaired to 100% is distinguishable from the real one by the very check meant to validate it, so the repair lands at 94.5% and 94.2%.
  • Utility barely moves. With every check restored, card stays at 27.5%, and loan reaches 16.5% with one of three seeds below the baseline (§7): constraint satisfaction, marginal fidelity and downstream utility are three separate axes. Tier-1 repair is useful for compliance gates, not as a utility fix.

8.4Tier 3: making a date violation impossible to express

Store each child date as log(1 + days since the parent account opened) and decode it as parent date + exp(max(value, 0)) − 1. Every decodable value is a non-negative lag. This works for GRDM because structure is sampled before attributes, so at decode time each row already knows its account and that account's date.

The six-column test (agg)

Hypothesis, stated so it could fail: if the missing utility is child-aggregate information that never reaches the denoiser, handing those statistics to GRDM as ordinary columns should raise synthetic→real AUROC. If the number did not move, the aggregate story would be wrong about cause.

10.1Design

  • Six columns, the ones the mechanism study measured: transaction count, mean balance, last balance and mean amount; order count and total order amount. Computed from the real training split only (792,600 transactions and 4,874 orders over 3,375 accounts); an account without orders gets zero.
  • On both account and disp. On account alone they would not help card: a card row's only parent is disp, and at one hop account is out of view (Figure 3).
  • Excluded on purpose: transaction code shares. VYBER KARTOU is a consequence of holding a card, so exposing it would hand the generator the label.
  • Unchanged: n_hops 1, all one-hop neighbours, sum aggregation, network size, T = 2,000, learning rate, 200,000 steps, the split, the seeds and every downstream feature builder. The config differs from the baseline only in its data directory.
  • No shortcut at evaluation. The feature builders never read agg_*; the evaluated matrices are 90 (card) and 97 (loan) columns, as in the baseline. For the score to rise, a chain must hold: GRDM generates a disp.agg_* value, a card whose existence correlates with it, transactions conditioned on account.agg_*, and those transactions must re-aggregate to something close to what the account declared. Nothing in the loss enforces that chain.

10.3What it means

The intervention targeted exactly the variable the diagnosis pointed at and moved the outcome in the predicted direction on both tasks and in every seed. That turns the aggregate story from a correlation into a supported causal claim. A fix delivered entirely through the input, without touching depth, pooling or the loss, did better than every network change at the same cost, and matched S5's card result with more loan signal (35.8% against 24.9%) and without its doubled run time.

10.4Before quoting it

  1. There are no fidelity numbers for agg. The paper's evaluation builds its metadata from the data directory and aborts on all three seeds with InvalidMetadataError: Column name ('agg_trans_n') does not exist in the table. Sampling is unaffected and all eight tables are written. Every earlier variant that lifted card above 40% cost Column Shapes (S2 −1.9, S5 −1.8, S12 −2.3, S7 −5.0 and S6 −11.3 points), so this missing column matters. S5 and S12 kept 1-HOP; S2, S6 and S7 did not.
  2. The six columns were chosen with downstream knowledge. This is not circular at evaluation time, but on a new schema nobody would know which six to pick. For AmEx it needs a mechanical rule, such as count plus mean, sum and last value for every numeric column of every child table.
  3. Most of the gap is still open. 0.688 against a real 0.869 on card is partial recovery, and loan (35.8%) trails reparam + S10 (43.6%).
11

Interpretation

  1. Fidelity metrics measure what GRDM does well. They compare marginals and pairwise correlations, which GRDM reproduces closely. None of them asks whether a statistic computed over a parent's child rows still relates to an outcome two or three tables away. A deep-schema synthesiser can score 96–99 on every published metric and carry little predictive structure. The ranking can even invert: ClavaDDPM trails GRDM on every Berka fidelity metric in the paper and carries more of the signal on both Berka tasks (card 60% against 29%, loan 43% against 7%; §5.5).
  2. The limitation is structural. The quantities that carry the Berka signal are child aggregates: balances, counts and order codes for loan default, balance and amount rollups for card ownership. At one hop GRDM never sees them for the labelled row, and at two hops the second hop is a capped sample pooled by a sum, so the true count is not an input. Training longer or tuning harder cannot supply information the input lacks.
  3. The synthetic data is empty, not biased. Synthetic→synthetic sits near chance, a real-trained model does no better on synthetic rows than a synthetic-trained one, and the collapsed aggregates have confidence intervals covering 0.5 in every seed. Mitigations framed as re-weighting, calibration or domain adaptation would target a problem that is not there.
  4. Fixing the visible symptom does not fix utility. Four independent attempts restored what a fidelity table or a rule check would flag (S1 marginals, S4 encoding, discrete diffusion, full constraint repair). None moved card utility; on loan, S1 and repair add 11–13 points with one seed in three falling below the baseline, against 33–40 points for the fixes that add cross-table information (agg, reparam + S10). Constraint satisfaction, marginal fidelity and downstream utility are separate axes, and a change can move them in different directions; S2 raised card utility while lowering fidelity.
  5. Information in the input beats capacity in the network. Adding the missing statistics as data (agg, no extra cost) did more for card than any change to the denoiser architecture except the one-seed S12, and S10 helped for the same reason: it supplies counts the network could not infer, and reparam + S10 is the best loan result. Depth matches agg on card (S5 50.4%, S7 49.8%, against 48.7%) only by widening the window; it gives less loan (S5 24.9%, S7 11.9%, against agg's 35.8%) and costs fidelity and twice the compute.
  6. The two tasks respond to overlapping fixes. Both lose cross-table dependency, and both gain from cross-table information: agg lifts both (loan 35.8%, card 48.7%), and so does two-hop depth (S2, S5). Loan also responds to balanced seeding (S3, 32.2%; the loan table gets 2.6 seed rows per batch) and most to exact child counts with S5 settings (reparam + S10, 43.6%), which move card less (34.5%). The loan rare-class collapse is a symptom, not the main cause (S1, ClavaDDPM). No tested configuration reaches 50% on both; agg combined with S3 or S10 is the most direct next test.
  7. Noise is a first-class result on small tasks. Seed 0 alone overstated S3 (53% against 32% at three seeds), S5 (37% against 25%) and reparam (17% against −3%) on loan, and understated S7 (−13% against 12%). With 19 positive test cases, three generator seeds is the minimum for any loan-default claim; card ownership, with 220, is where conclusions should rest.
  8. For the AmEx program. The planned dispute schema (17 tables in 6 layers) is deeper than Berka, so the same failure should be expected unless the generator receives cross-table statistics. Quality gates need a downstream-utility check and dependency checks in addition to fidelity; financial checks must be stated over whole transaction sequences, not end balances; repairs should target real-data rates; and any aggregate rule should be mechanical (every numeric column of every child table), not a hand-picked list.
12

Limitations

  • Small loan test set. 19 positive cases; real-only bootstrap CI [0.870, 0.989]. Loan magnitudes are indicative only.
  • Provisional rows. S4, S6 and S12 have one generator seed; the California guards for S2–S7 have one seed each.
  • agg is incomplete as evidence. No fidelity numbers yet, and its six columns were chosen using knowledge of the downstream tasks.
  • The card task is a dependency probe, not a forecast. Its features include account history that partly follows card issue; no date cut separates cause from effect.
  • Downstream models. Utility rests on one untuned XGBoost setup; the DeepSets probe agrees but was run on the baseline generator only.
  • Coverage. Utility was measured on Berka and California only. CCS's 1-HOP gap is not root-caused; Instacart 05, MovieLens and RelBench-F1 were not attempted, and only the GRDM column of the paper's Table 1 was reproduced.
  • ClavaDDPM comparison. ClavaDDPM's Berka runs saw the test rows; no leakage-free ClavaDDPM Berka run exists. GRDM's own leaky-to-clean difference was at most 0.017 AUROC.
  • Unexplained results. Why S5 lifts card to 50% without restoring any aggregate family's linear association (§6.5) is not established, nor which of its three changes gives reparam + S10 its loan result. reparam's fidelity is measured in the lag representation.
  • Earlier loan numbers. Until 5 October the loan-default window ended 185 days before each loan. Every loan number in this report uses the corrected window; the archived pages and the August write-ups in docs/ still carry the old ones.
  • No ceiling. The flatten baseline failed, so it is unknown whether 48.7% on card is near or far from what a generator could reach on this data.

Recommendations and next steps

In priority order. The first two are cheap and gate the headline result.

  1. Restore agg's fidelity numbers. Declare the agg_* columns in the evaluation metadata (built from the data directory in main.py) and re-run only the evaluation on the existing samples. Until then agg cannot be said to keep GRDM's fidelity.
  2. Check the agg chain. Measure whether generated transactions re-aggregate to the agg_* values their account declares. Nothing in the loss enforces it, the data is on disk, and it would show where the remaining card gap is lost.
  3. Turn the six columns into a rule. Count plus mean, sum and last value of every numeric column of every child table, applied mechanically to every parent. This is the version that transfers to AmEx, and it tests whether the gain came from these six columns or from denormalisation in general.
  4. Stack agg with S3 or S10, three seeds. agg is the best combined result (35.8% loan, 48.7% card) and reparam + S10 the best loan result (43.6%); they change different parts of the pipeline (input columns, seed sampling, degree features) and are the most plausible route to 45–50% on both tasks.
  5. Run S3 + S10 at three seeds. Shallow balanced training with exact counts at one hop; never run.
  6. Fix the flatten baseline's numerics (gradient clipping, loss scaling) to obtain a ceiling.
  7. Finish S12 (seeds 1–2 and the California guard) if compute allows; it holds the highest single card number.
  8. For AmEx quality gates: adopt downstream utility (balanced accuracy and AUROC, three seeds) and dependency fidelity as explicit gates; state financial invariants over the full sequence; keep post-hoc repair for compliance (Gates 3 and 4) and aim it at real-data rates.
  9. Housekeeping. Done on 5 October: agg and the two repair variants are in FIX_LABELS, and the commentary in docs/downstream/RESULTS_downstream.md was corrected. Glossary of acronyms and terms

Models and methods

GRDM
Graph-Conditional Relational Diffusion Model (Ketata et al., NeurIPS 2025). Generates a whole relational database as one graph: structure first, then all attributes by joint diffusion. The model studied here.
ClavaDDPM
Multi-relational synthesis with cluster-guided diffusion models (Pang et al., NeurIPS 2024). Generates tables parent to child, conditioned on learned cluster labels; GRDM's main baseline.
DDPM
Denoising diffusion probabilistic model. Learns to reverse a process that adds Gaussian noise over T steps; sampling starts from noise and removes it step by step.
T
Number of diffusion timesteps; 2,000 here.
Multinomial diffusion
Diffusion for categorical values that moves towards a uniform distribution over classes instead of adding Gaussian noise (the discrete variant).
GNN
Graph neural network. A network whose layers update each node from its neighbours.
GraphSAGE
A message-passing layer that combines a node's own features with an aggregate of its neighbours' (a sum in GRDM). The heterogeneous version keeps separate weights per table and per relationship.
MLP
Multilayer perceptron, a plain feed-forward network.
DeepSets
A permutation-invariant network for sets: encode each element, pool (mean, max), predict. Used as a second downstream model (§9.5).
XGBoost
A gradient-boosted decision-tree library; the downstream model throughout.
n_hops, K
How many foreign-key edges away the denoiser looks when generating a row; also the number of GNN layers. Published value 1.
num_neighbors
Maximum neighbours sampled at each hop; −1 means all. -1 16 means all at hop 1 and 16 at hop 2.
gnn_aggr
The statistic used to pool neighbours: sum by default; S8 uses sum, mean, max and standard deviation.
Seed row
The row whose noise prediction is scored in a training step. GRDM draws seed rows uniformly over all rows.
α (seed_balance_alpha)
S3's re-weighting of seed rows by table size−α; 0 is uniform, 1 gives every table equal weight. 0.5 is used.
Degree features
S10: the exact number of children per relationship, log-scaled, attached to every row.
Self-conditioning
S11: the model's own first estimate of the clean data is fed back as input in a second pass.
Residual connection
S9: each GNN layer adds to its input instead of replacing it.
Structure sampling
GRDM's first stage: draws how many children each parent gets from the real degree distribution, before any attribute exists.
Dimension table
A lookup table held fixed and only conditioned on (Berka's district).
Label encoding
Mapping categories to integers 0…K−1; GRDM diffuses these integers as numbers.
Quantile transform
Mapping each column to a standard normal distribution before diffusion.
Reparameterisation
Changing how a value is stored; here a child date becomes log(1 + days since the parent account opened).
Denormalisation
Copying information from related tables into a table as extra columns (agg).
Tier 1 / Tier 3
Tier 1: edit finished samples so constraints hold (post-hoc repair). Tier 3: change the representation so a violation cannot be expressed.

Fidelity metrics

SDV, SDMetrics
Synthetic Data Vault, an open-source synthetic-data library; SDMetrics is its metrics package, used by the paper's evaluation.
Cardinality
Similarity of the number of child rows per parent, real against synthetic, averaged over relationships.
Column Shapes
Similarity of each column's marginal distribution, averaged over columns.
Intra-Table Trends
Similarity of the correlation of every column pair within a table.
k-HOP
Inter-table trends: the same comparison for column pairs from tables k links apart; 1-HOP is parent and child.
AVG 2-WAY
Average of all column-pair scores, intra-table and inter-table.
KS
Kolmogorov–Smirnov statistic: the largest gap between two cumulative distributions; 0 means identical.
TV, TVD
Total variation distance between two categorical distributions.
Wasserstein distance
The least "transport" needed to turn one distribution into another; repair costs are given in real standard deviations.

Downstream metrics and statistics

AUROC, ROC-AUC
Area under the receiver operating characteristic curve: the probability that a random positive case is ranked above a random negative one. 0.5 is chance, 1 is perfect.
ROC
Receiver operating characteristic: true-positive rate against false-positive rate over all thresholds.
AP
Average precision: area under the precision–recall curve.
R²
Coefficient of determination. 1 is perfect; 0 equals always predicting the mean; negative is worse than that.
F1, macro-F1
Harmonic mean of precision and recall; macro-F1 averages it over classes with equal weight.
Balanced accuracy
Mean of per-class recall; 0.5 is chance for two classes. Robust to imbalanced labels.
Accuracy
Share of correct predictions; misleading when one class dominates (§5.2).
Signal retained
(synthetic − floor) / (real − floor), with floor 0.5 for AUROC and 0 for R² and macro-F1 (§3.2).
Univariate AUROC
The AUROC of a single feature used directly as a score; no model involved.
CI
Confidence interval; here a 95% interval from the bootstrap.
Bootstrap
Resampling the evaluation rows with replacement to estimate uncertainty; 400 resamples in the mechanism study.
SD, ±
Standard deviation, over all repeats unless stated.
Spearman ρ
Rank correlation between two orderings.
Point-biserial correlation
Correlation between a binary label and a numeric feature, used in A6.
TRTR, TSTR, TRTS, TSTS
Train on real or synthetic, test on real or synthetic: the four cells of the cross-domain matrix (§9.1).
Seed
A random seed. A generator seed is one full GRDM training; an XGBoost seed is one downstream fit.

Reproducing the main results

# environment: shared conda env, always through conda run
cd /scratch/s25017/ClavaDDPM/rdb-diffusion
# code: upstream commit bc0fb67 plus the uncommitted local changes in this working tree

# fidelity reproduction (3 seeds each; idempotent, resumes after kills)
scripts/resume_runs.sh                                   # berka
RDBDIFF_DATASET=california scripts/resume_runs.sh
RDBDIFF_DATASET=ccs scripts/resume_runs.sh

# leakage-free split, generator, downstream utility
conda run -n tabsyn python -m downstream.make_berka_split
RDBDIFF_DATASET=berka_split scripts/resume_runs.sh 0 1 2
conda run -n tabsyn python -m downstream.run --dataset berka_split
conda run -n tabsyn python -m downstream.run --dataset california

# diagnosis
conda run -n tabsyn python -m downstream.diagnose
conda run -n tabsyn python -m downstream.diagnose_aggregates

# a fix variant, e.g. S3 (any flag set goes in RDBDIFF_EXTRA_ARGS)
RDBDIFF_DATASET=berka_split_s3 RDBDIFF_EXTRA_ARGS="--seed_balance_alpha 0.5" scripts/resume_runs.sh 0 1 2
conda run -n tabsyn python -m downstream.run --dataset berka_split_s3

# dependency checks and repair
conda run -n tabsyn python -m dep_fidelity.run --synthetic <run>/synthetic_database --label <name>
conda run -n tabsyn python -m dep_fidelity.run_repair --dataset berka_split --seeds 0 1 2 --write

# mechanism study
conda run -n tabsyn python -m downstream.ratio_report
conda run -n tabsyn python -m downstream.crossdomain --dataset berka_split
conda run -n tabsyn python -m downstream.feature_compare --dataset berka_split
conda run -n tabsyn python -m downstream.aggregate_validation

# six-column test
conda run -n tabsyn python -m downstream.build_agg_dataset
RDBDIFF_DATASET=berka_split_agg scripts/resume_runs.sh 0 1 2
conda run -n tabsyn python -m downstream.run --dataset berka_split_agg
conda run -n tabsyn python -m downstream.crossdomain --dataset berka_split_agg

# re-score every downstream result after a change to the task code (no GPU; logs in logs/scoring/)
scripts/rescore_downstream.sh

# regenerate tables
conda run -n tabsyn python -m downstream.report
